# Spotify Soloist as Riko's desktop player (2026-11-11)

Owner decision (verbatim choice): "Riko manages Soloist herself: tray Start/Stop
keeps working, auto-updates from Spotify's official download server before
builds expire, no third-party helper".

Why: on 2026-11-11 every librespot-based player (Arch spotifyd 0.4.2 AND
librespot 0.8.0) stopped getting audio keys (`error audio key 0 1` -> silent
playback, auto-skip every ~8 s; docs/SPOTIFY_NOTES.md incident section).
Spotify's answer is **Spotify Soloist**, its official headless Connect player:
https://developer.spotify.com/documentation/soloist . soloistd
(github.com/MopigamesYT/soloistd, MPL-2.0) was reviewed as prior art only — no
code is copied and it is not a dependency.

## Facts (from the official docs, verified 2026-11-11)

- Daemon: `soloist -n NAME -k KEY [options]`. Required: `-n/--device-name`,
  `-k/--api-key`. Storage: `-D/--data-dir`, `-C/--cache-dir`,
  `-z/--cache-size MB` (0 = unlimited, else >= 100). Audio: PipeWire or
  PulseAudio, default output; `-d/--pipewire-device`, `-i/--initial-volume
  0..100`. `-w/--ws ADDR:PORT` enables the local WebSocket API (port 0 = OS
  picks; then the data dir holds `ws.addr`/`ws.port`, plus `soloist.pid`).
  `-p/--pair` = pair through Spotify Connect, store session, exit.
  `-v` verbose, `-V` version.
- Exit codes: 0 ok, 1 general failure (incl. "another Soloist process already
  using the data directory"), **10 = build expired**.
- **Builds expire 90 days after their build date.** `soloist --version` prints
  e.g. `soloist 1.3.10.61 build 1794376870 (20261111) (g19412df6ea)
  (linux/x86_64)` — the `(YYYYMMDD)` field is the build date.
- Official archive (do NOT redistribute; each user downloads their own):
  `https://soloist-builds.spotifycdn.com/soloist_release_x86_64.tar.gz`
  (also `_arm64`, `_arm32`). Contains `soloist`, `CHANGELOG.md`,
  `THIRD_PARTY_LICENSES.txt`. HEAD returns `etag` + `last-modified`
  (2026-11-11: etag "b56e680e8235f2a929f89dcff1c8f618", 13.8 MB).
- Auth: (1) a **Soloist API key** generated by the owner (Premium account) at
  https://developer.spotify.com/dashboard/soloist — a secret, passed on every
  start; (2) a Spotify Connect session created the first time the owner picks
  the device in a Spotify app on the same LAN; stored in the data dir and
  restored on restart. No browser login, no username/password.
- The WebSocket API has NO authentication — bind 127.0.0.1 only.
- Full doc text captured for implementers:
  `~/.hermes/cache/browser-use/workspace/20261103_172853_8b9264/soloist_docs.json`
  (keys: concepts/overview, concepts/authentication, reference/command-line,
  reference/downloads-and-updates, reference/soloist-ctl,
  reference/websocket-api, howtos/basic-integration, tutorials/getting-started,
  features).

## Contract

Config (`character_config.yaml`, `desktop.music`):
- `player: soloist | spotifyd | external | off` — NEW, default `soloist`.
  Legacy `spotifyd: managed|external|off` keeps working when `player` is
  absent (back-compat), but the shipped config sets `player: soloist`.
- `device_name` default "Riko" (same as today; never the persona name).
- `soloist.cache_size_mb` default 500; `soloist.initial_volume` optional;
  `soloist.pipewire_device` optional; `soloist.auto_update: true`.

Files (all owner-owned, never in the repo):
- API key: `~/.config/riko/soloist.key` — mode 0600, written BY THE OWNER
  (one line). Riko reads it, never logs it, never sends it to the hub, never
  echoes it in tray/chat/errors (redact the key value from any captured
  stderr before surfacing). Missing/empty key -> tray says exactly how to
  create it (dashboard URL + `install -m 600 /dev/stdin
  ~/.config/riko/soloist.key` style instruction) and does not start.
  Wrong permissions (group/other readable) -> refuse with a fix-it line.
- Binary: `~/.local/share/riko/soloist/bin/soloist`; metadata
  `~/.local/share/riko/soloist/release.json` ({etag, last_modified, version,
  build_date, installed_at, sha256}).
- Data dir (session): `~/.local/share/riko/soloist/data`; cache
  `~/.cache/riko/soloist`.

Lifecycle (`riko/music/soloist.py`, same seams as `riko/music/spotifyd.py`:
injectable `which/popen/http/log/clock`, never a real network or process in
tests):
- Start: ensure binary (install if missing), check key, spawn
  `soloist -n Riko -k <key> -D data -C cache -z 500 -w 127.0.0.1:0
  [-i N] [-d dev]` with env scrubbed of the key otherwise; early-exit
  detection like spotifyd (exit 1 -> surface Soloist's own stderr, redacted;
  "already using the data directory" -> say another Soloist is running).
- Never run spotifyd and Soloist at the same time under the same name; with
  `player: soloist` spotifyd is never started.
- Stop: SIGTERM, then SIGKILL after a grace period; idempotent.
- First run / no stored session: tray + log line "Open Spotify on your phone
  or PC and pick 'Riko' in the device list once — she'll remember it".
  (Detect via the WebSocket status if available, else via the data dir.)

Auto-update (official CDN only; URL hard-coded, https only, host must be
`soloist-builds.spotifycdn.com`):
- Check at desktop start, at every player Start, and every 6 h while the
  desktop runs: HEAD the archive; if etag/last-modified differ from
  release.json (or binary missing) -> download (size cap 100 MB) to a temp
  dir under the install dir, extract ONLY `soloist` (reject absolute paths,
  `..`, symlinks), chmod 755, run `<new> --version` (timeout 10 s) and parse
  the build date, then atomically rename over the old binary and write
  release.json. If the player is running: restart it only when not playing
  (WebSocket state) OR the running build expires within 3 days; else defer
  to the next idle moment.
- Exit code 10 at any time -> force update + restart once; if that fails,
  tray error "Soloist build expired and the update failed: <reason>".
- Failed checks never interrupt playback; they log once per failure kind.
- Tray Music menu: Start/Stop player (as today), "Update Soloist now", and a
  status line "Soloist <version>, expires <date>" (warn when < 7 days).

Ducking: replace MPRIS ducking for Soloist with the WebSocket API volume
control (read current volume, lower to duck fraction while she speaks,
restore) — same `session.on_speak` hook as `MprisDuck`. If the WS is
unavailable, ducking silently no-ops.

Hub: no API change (device stays "Riko"). Fix the misleading 403 message:
Spotify answers `403 "Player command failed: Restriction violated"` on the
first play to a just-registered device; transfer-then-retry once before
raising, and only mention Premium when the body is NOT "Restriction
violated" or the retry also fails.

Docs: docs/SPOTIFY_NOTES.md gets a pointer here; docs/API.md/TOOLS.md only if
anything user-visible changes; README/setup steps for the owner: create the
key, write the key file, Start player, pick "Riko" once on the phone.

## Owner steps (once)
1. https://developer.spotify.com/dashboard/soloist -> generate API key.
2. In a terminal (key never goes in chat):
   `install -D -m 600 /dev/stdin ~/.config/riko/soloist.key` then paste the
   key, Enter, Ctrl-D.
3. Restart desktop.py -> tray Music -> Start player.
4. On the phone's Spotify app pick "Riko" once.
